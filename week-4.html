FHIR APIs

Week 4 · ~10 h (SMART often runs over)

FHIR is the API layer apps, payers and data-sharing rules build on: US certified EHRs must offer FHIR APIs, and Canada's national profiles are FHIR R4 too. When a patient's phone shows last month's lab results, or a clinician's screen shows a warning card from a service the hospital bought, a FHIR request was made somewhere. When those requests are careless, the failures are quiet. An app that reads only the first page of a search shows twenty labs out of two thousand and looks fine. An app that asks for every scope holds far more of someone's record than it needs. A feed that never checks its output against the national profile hands the next system data it can't use.

Week 0 taught read, search and conditional update. This week we ask better questions and check the answers. We load ten synthetic patients into a FHIR server and search them properly: chains, includes, paging and bulk export. We separate what data must be exchangeable from how it is shaped, and validate resources against the US and Canadian profiles, by hand and as a CI gate. Then we look at the two standards that let outside software into the clinical workflow: SMART on FHIR, which lets an app act for a user, and CDS Hooks, which lets a service speak up while a clinician is looking at a chart.

Every command on this page was run on 31 Oct 2026 against the course lab: HAPI FHIR 8.12.0 in Docker, Synthea (master build of 21 Oct 2026), the HL7 FHIR validator 7.0.3 on OpenJDK 25, Node 20 with fhirclient 3.0.1, Python 3.12 and jq 1.7, plus the public SMART launcher sandbox. The outputs are copied from one run of the lab script. Yours will differ in server ids, timestamps and random values.

A server with patients in it

Search

A FHIR search is a GET on a resource type with parameters, and the answer is a Bundle of type searchset. Three parts of that Bundle matter as much as the resources inside it: total, how many matched; entry, the ones on this page; and link, where to go next. _count asks for a page size, and _elements trims each resource so we can read the output:

Following the next link

The first query matched ten patients and returned three. The next link is not our query with an offset: HAPI stored the result set and handed us a _getpages id. Treat paging links as opaque; follow them, don't build them.

Then the trap. Corie, the 101-year-old, has 2,067 laboratory Observations. The plain search returned 20 of them, and total was null: HAPI hadn't counted yet and left it out, which the spec allows. Nothing in the response is an error. An app that renders entry and stops has just told a clinician that this patient's lab history is twenty results long. _total=accurate made the server count. The spec is explicit that page size is a request: servers “SHALL NOT return more resources than requested … but may return less”. The only correct client follows next until there is none. Ours is ten lines of shell:

#!/bin/sh
# Print every resource a FHIR search matches, one JSON per line,
# following Bundle.link "next" until the server stops sending one.
url=$1
while [ -n "$url" ]; do
  page=$(curl -s "$url")
  printf '%s\n' "$page" | jq -c '.entry[]?.resource'
  url=$(printf '%s\n' "$page" |
        jq -r '.link[]? | select(.relation == "next") | .url')
done

It returned all 2,067. With _count=500 the same loop needed 5 round trips instead of 104, and once you have every page you can ask questions like which tests dominate the record.

Chained parameters

Often what you know isn't on the resource you want. You want Observations, but you know the patient's name or birth date, which live on Patient. A chained parameter follows a reference inside the search: subject:Patient.name=Beahan375 means “Observations whose subject is a Patient whose name matches Beahan375”. _has goes the other way: Patients pointed at by a Condition with a given code. Each replaces a loop of requests in your code with one the server can plan:

$ curl -sG $F/Observation \
  --data-urlencode 'subject:Patient.name=Beahan375' \
  --data-urlencode 'code=http://loinc.org|4548-4' \
  -d _summary=count | jq .total
65
$ curl -sG $F/Observation \
  --data-urlencode 'patient.birthdate=lt1960-01-01' \
  --data-urlencode 'code=http://loinc.org|4548-4' \
  -d _summary=count | jq .total
76
$ curl -sG $F/Patient -d _elements=name --data-urlencode \
  '_has:Condition:patient:code=http://snomed.info/sct|59621000' \
  | jq -r '.entry[].resource.name[0].family'
Beahan375
Gibson10

One patient's HbA1c results (LOINC 4548-4), the same for everyone born before 1960, and the patients with essential hypertension (SNOMED CT 59621000). curl -G --data-urlencode encodes the | between system and code; hand-built URLs break there. In production, chain on subject:Patient.identifier=system|value, not names: as in week 3, identity is an identifier with a system. And the server decides which chains it supports. Its CapabilityStatement lists the search parameters, and a server may ignore one it doesn't know, so check the self link to see what was applied.

_include and _revinclude

A medication list needs the prescriber's name. Fetching each Practitioner is one request per row; instead, ask the server to include referenced resources in the same Bundle. _include follows references out of the matches, _revinclude pulls in resources that point back at them:

$ modes() { jq -r '.entry[] |
  "\(.search.mode) \(.resource.resourceType)"' | sort | uniq -c; }
$ curl -s "$F/MedicationRequest?patient=$pid&_count=5\
&_include=MedicationRequest:requester" | modes
      1 include Practitioner
      5 match MedicationRequest
$ curl -s "$F/Patient?_id=$pid&_revinclude=Condition:patient" |
  tee rev.json | modes
    141 include Condition
      1 match Patient
$ jq '.total' rev.json
1

search.mode says why each entry is there: match or include. Five orders by one clinician brought one Practitioner: includes are deduplicated. The reverse include returned one Patient and 141 Conditions, and total still says 1, because it counts matches only. Never compute “how many results” by counting entries. And ask only for what the screen shows: a _revinclude on a long-lived patient can be huge.

Bulk export

Analytics, payers and quality reporting need everything, and paging through a population would take hours and pin the server. The Bulk Data Access specification defines $export: kick off a job, poll a status URL, and download newline-delimited JSON (one resource per line) when it's ready:

$ poll=$(curl -s -D - -o /dev/null \
  -H 'Accept: application/fhir+json' -H 'Prefer: respond-async' \
  "$F/\$export?_type=Patient,Condition" |
  tr -d '\r' | awk '/^Content-Location/ {print $2}')

The kick-off returned a Content-Location to poll; we polled until the status was 200 and saved the manifest, which lists one file per resource type. Note requiresAccessToken: true. In production each of these calls carries a token from SMART Backend Services (an app authenticating as itself, with no user), and the files are as sensitive as the EHR. Our lab server has no authentication, which is fine for synthetic data and nothing else.

What versus how

Base FHIR is deliberately loose: almost every element is optional, codes can come from any system, and extensions can carry anything. That's why FHIR fits every country, and why two systems that both “speak FHIR” can still fail to understand each other. Countries fix this in two layers.

The first says what must be exchangeable, in plain terms: demographics, problems, medications, allergies, lab results, vital signs, notes. In the US that is USCDI, the United States Core Data for Interoperability; in Canada, CACDI, the Canadian Core Data for Interoperability, published by CIHI. Neither says anything about JSON.

The second says how those elements look in FHIR: profiles that make elements required, bind them to value sets and define extensions. US Core is “updated annually to support the latest requirements” of USCDI. In Canada, CA Baseline is the national starting point, and CA Core+, the guide aligned with CACDI, is still a draft.

Validation

A profile is only useful if something checks it. The reference tool is the HL7 FHIR validator, one Java jar. Give it resources, a FHIR version, one or more implementation guides (-ig, downloaded as packages into ~/.fhir) and a profile. It checks codes against value sets too, asking the terminology server at tx.fhir.org about ones it can't resolve locally, so it needs the network.

Two errors of one kind. Synthea adds two extensions of its own, disability-adjusted and quality-adjusted life years (DALY and QALY). The warnings need explaining too, since “every Synthea error is explained” is this week's bar, and a stricter profile can turn a warning into an error. The notes (not shown) are extensions that match no slice the profile names, which is normal.

Validation in CI

Validation you run by hand stops the week you get busy, so put it in CI. The validator does the hard part: it exits non-zero when any file has an error, and CI fails a step on a non-zero exit. Our gate is a short script:

#!/bin/sh
# CI gate: validate FHIR Patients against CA Baseline.
# The validator exits non-zero if any file has an error, and
# set -e passes that on, so the CI job fails.
set -e
P=http://hl7.org/fhir/ca/baseline/StructureDefinition
java -jar validator_cli.jar "$@" -version 4.0.1 \
  -ig hl7.fhir.ca.baseline#1.2.0 -profile $P/profile-patient \
  -allow-example-urls true > validation.log 2>&1 || {
  grep -E '^-- |^\*FAILURE|Error @' validation.log
  exit 1
}
grep -E '^-- |^Success' validation.log

Here it passes, and then fails after we simulate a mapping regression: someone drops the gender table and writes the HL7 v2 code F straight into FHIR.

SMART on FHIR

Real EHR FHIR APIs require a token, and SMART App Launch is how an app gets one: OAuth 2.0 plus conventions for discovery, scopes and launch context. In an EHR launch the clinician is already in the chart and opens the app from inside it; the EHR passes the app an iss (the FHIR base URL) and an opaque launch value, which the app trades for a token tied to that patient and user. In a standalone launch the app starts on its own, like a patient's phone app, and the patient is chosen during login.

Scopes say what the token allows. In SMART v2, patient/Observation.rs means read and search Observations for the patient in context (v1 wrote patient/Observation.read). Ask for the narrowest scope the screen needs: a labs app has no business holding patient/*.rs, and v2 can narrow further with a search parameter, patient/Observation.rs?category=…|laboratory. The server may grant less than you asked for, so read scope in the token response.

Every SMART app must use PKCE (Proof Key for Code Exchange). The app makes a random verifier and sends only its SHA-256 hash, the challenge, when it asks for authorization. To swap the resulting code for a token it must show the verifier, so someone who intercepts the code can't use it. SMART servers must support S256 and must not support plain.

Walking the flow with curl

The public SMART launcher at launch.smarthealthit.org simulates an EHR, with an authorization server and a FHIR server of synthetic patients. Discovery comes first: a SMART server publishes its endpoints at .well-known/smart-configuration under the FHIR base. Then we play the EHR and the app by hand. The authorization request came straight back to our redirect URI with a code and our state. The wrong verifier was refused because its hash didn't match the challenge. The right one got a token, and the response carries the launch context, the patient and encounter the EHR had open: that's how an EHR-launched app knows whose chart it's in.

Two things there are sandbox behaviour your app must not rely on. We used the same code twice and both worked; OAuth 2.0 says a code must not be used more than once. And a token scoped to Observations read Conditions: the launcher's FHIR server doesn't enforce scopes. A real EHR does, so test scope handling against the vendor's sandbox.

A SMART app in TypeScript

In practice the SMART JavaScript client, fhirclient, does discovery, state, PKCE and the token exchange. Here is the server-side Express version, in the shape of week 0's TypeScript app. The launch route starts authorization:

// The EHR opens /launch?iss=<FHIR base>&launch=<opaque>
app.get("/launch", (req, res, next) => {
  smart(req, res).authorize({
    clientId: "labs-app",
    scope: "launch openid fhirUser patient/Observation.rs",
    redirectUri: "/app",
  }).catch(next);
});

and the redirect route finishes it and reads labs and vital signs for the patient in context:

// The authorization server redirects back here with ?code=&state=
app.get("/app", async (req, res, next) => {
  try {
    const client = await smart(req, res).ready();
    const lines = [`patient ${client.patient.id}`,
                   `scope ${client.state.tokenResponse?.scope}`];
    for (const cat of ["laboratory", "vital-signs"]) {
      const bundle = await client.request<Bundle>(
        `Observation?patient=${client.patient.id}` +
        `&category=${cat}&_sort=-date&_count=4`);
      lines.push(`-- ${cat}`,
                 ...(bundle.entry ?? []).map((e) => show(e.resource)));
    }
    res.type("text/plain").send(lines.join("\n") + "\n");
  } catch (e) {
    next(e);
  }
});

CDS Hooks

SMART puts your app in front of the clinician when they open it. CDS Hooks works the other way: the EHR calls your service at moments in the workflow called hooks, and shows what you return. patient-view fires when a chart is opened; order-select and order-sign fire while orders are written. You answer with cards: a summary, an indicator (info, warning or critical), a source, and optionally suggestions or links that launch a SMART app.

A service describes itself at {base}/cds-services, including a prefetch template: FHIR queries the EHR runs and sends along, so the service doesn't call back while a clinician waits. Ours shows the latest HbA1c:

A1C = ("Observation?patient={{context.patientId}}"
       "&code=http://loinc.org|4548-4&_sort=-date&_count=1")
SERVICE = {
    "hook": "patient-view",
    "id": "a1c-latest",
    "title": "Latest HbA1c",
    "description": "Shows the most recent HbA1c, or warns if none.",
    "prefetch": {"a1c": A1C},
}
SOURCE = {"label": "Week 4 demo service (synthetic data)"}


def fetch_a1c(req):
    """Used only when the EHR sent no prefetch: ask its FHIR server."""
    query = A1C.replace("{{context.patientId}}",
                        req["context"]["patientId"])
    http = urllib.request.Request(f"{req['fhirServer']}/{query}")
    token = (req.get("fhirAuthorization") or {}).get("access_token")
    if token:
        http.add_header("Authorization", f"Bearer {token}")
    with urllib.request.urlopen(http, timeout=10) as resp:
        return json.load(resp)


def cards(req):
    bundle = req.get("prefetch", {}).get("a1c")
    if bundle is None:
        bundle = fetch_a1c(req)
    entries = bundle.get("entry", [])
    if not entries:
        return [{"summary": "No HbA1c on file", "indicator": "warning",
                 "source": SOURCE}]
    obs = entries[0]["resource"]
    q = obs["valueQuantity"]
    when = obs["effectiveDateTime"][:10]
    return [{"summary": f"Latest HbA1c {q['value']} {q['unit']} ({when})",
             "indicator": "info", "source": SOURCE}]

Cards interrupt busy people. Use the narrowest hook that fits, return no card when there's nothing to say, and keep the summary short (the spec caps it at 140 characters). A service that cries wolf trains clinicians to dismiss every card, including the one that matters.

Patient access, information blocking, TEFCA and Inferno

Much of this exists because of regulation. In the US, the ONC Cures Act Final Rule requires certified health IT to offer a standardized FHIR API with SMART authorization, including for patients reaching their own records, and its information blocking rules make it a problem to interfere with access to, exchange or use of electronic health information, outside listed exceptions. TEFCA, the Trusted Exchange Framework and Common Agreement, is the US national network of networks. In Canada, health care is run by the provinces and territories, and what their systems must support is set mostly by them and their programs, with CACDI and HL7 Canada's guides as the shared national reference.

To check conformance, Inferno, ONC's open test tool, runs test kits against a FHIR endpoint: US Core profiles and searches, SMART launch and bulk export. We did not run Inferno for this page.
