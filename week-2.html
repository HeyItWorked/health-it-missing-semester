Data + SQL

Week 2 · ~10 h

Much of the job is answering questions from clinical data. A quality nurse wants to know which patients with diabetes are badly controlled. An emergency department manager wants visits per month to plan staffing. A researcher wants everyone whose blood pressure was high last year. Each request sounds like one query, and each one hides decisions: which code counts as diabetes, what “last year” means, whether the count is of patients or of visits, what unit the number is in. The data is coded, unit-laden and messy, so two honest queries can disagree, and you have to explain why.

Getting this wrong has consequences you can't see from the query. Count encounters instead of patients and a clinic looks busier than it is. Compare a glucose in mg/dL against a threshold in mmol/L and every patient becomes diabetic. Search on display text and patients with prediabetes land on a diabetes outreach list. Lose a care gap in a join and the patient who most needs a phone call never gets one.

This lecture generates one synthetic population, exports it twice (as CSV and as FHIR), loads the CSV into PostgreSQL and answers five clinical questions twice: once in SQL, once with jq over the FHIR files. Then we explain every number that differs. Along the way we look at the code systems that make clinical data comparable, a clinical note that holds facts the codes don't, a FHIR search against a local server, and the Canadian version of the data.

Every command on this page was run on 31 Oct 2026 against the course lab: Synthea (master build of 21 Oct 2026), PostgreSQL 16.11 in Docker (postgres:16-alpine), jq 1.7 and a local HAPI FHIR 8.12.0 server. The outputs are copied from one run. Yours will differ in timestamps and container ids; with the same seeds, the patients and counts should match.

Already the shapes leak information differently. The CSV has a CODE column but no column saying which code system it belongs to; you have to know that observation codes are LOINC. It has one VALUE column for both numbers and words, with a TYPE column telling them apart, and it stores times in UTC (the Z). The FHIR resource names its code system as a URI, puts the number in a valueQuantity with a UCUM unit, writes the same moment with a local offset (-04:00), and keeps two decimals: 8.21 where the CSV says 8.2. Every one of those differences shows up in a count later.

The schema in load.sql creates six tables with the CSV column names and loads them with \copy. The interesting part is the observations table:

-- VALUE is text: one column holds numbers and coded answers.
CREATE TABLE observations (
  date timestamptz, patient uuid, encounter uuid,
  category text, code text, description text,
  value text, units text, type text);

-- Cast once, at load time, and only the rows that are numbers.
ALTER TABLE observations ADD COLUMN num numeric;
UPDATE observations SET num = value::numeric
 WHERE type = 'numeric';

Most columns get real types (uuid, timestamptz, date), so a malformed date fails the load instead of hiding in a text column. VALUE can't be numeric, because it also holds answers like “Never smoked tobacco”. So we keep it as text and add a num column, filled once at load time for the rows whose TYPE says numeric. Every query below uses num. The NOTICE lines are DROP TABLE IF EXISTS saying there was nothing to drop; they make the script safe to re-run.

Three lessons in one file. Compared as text, '99.1' > '126' is true, because strings compare character by character, so the text query finds 321 “high” glucose results where the numeric one finds 12. Nothing warned us. Casting the whole column, on the other hand, fails loudly on the first word it meets, which is the better kind of failure. And two patients have a wellness encounter dated after their death: Synthea records a death certification as a visit. A query for “patients seen in the last year” would count one of them. Real EHR data has its own versions of this: placeholder dates, test patients, results filed against the wrong visit. Find them before you trust a count.

Code systems

Clinical data is comparable across systems only because the important fields are coded. Each code system covers one kind of thing, and a code means nothing without its system: 4548-4 is HbA1c in LOINC and nothing in particular anywhere else. The ones you will meet first:

LOINC, SNOMED CT, UCUM and RxNorm are there, and so are code systems you didn't ask for: the claims and explanation-of-benefit resources carry CMS Blue Button codes, because Synthea models US insurance. The rule that follows from all this is the one to remember: match on system + code, never on display text. Display text is for people. It changes between releases, differs between vendors and is matched by substrings you didn't intend, as question 4 shows.

Licences matter when you ship code that contains code lists. CPT, the US procedure codes used in billing, is licensed by the AMA. SNOMED CT is free to use in member countries but still licensed: in the US through the NLM, in Canada through Canada Health Infoway. LOINC is free under its own licence. RxNorm comes from the NLM.

Canada: diagnoses in hospital data are coded in ICD-10-CA and procedures in CCI, both maintained by CIHI, not the US ICD-10-CM. Drugs are identified by the Health Canada DIN, and the Canadian Clinical Drug Data Set (CCDD) plays the role RxNorm plays in the US. LOINC, SNOMED CT and UCUM are shared.

Five questions, two ways

Now the real work. We write five clinical questions, answer each in SQL, then answer it again with jq over the FHIR export. jq is the right second tool: it reads the same JSON a FHIR server returns, so the habits carry over to API work in week 4. Three jq moves cover most of it: filter by resourceType, follow subject.reference back to the patient, and read code.coding to match system + code. jq -n with inputs streams every file on the command line through one program, so output/fhir/*.json is the whole population.

Before writing either query, pin the question down. Who is counted (patients, visits, results)? Over what window, in which time zone? Which codes, in which unit? We pin “the last year” to a literal date, 2025-10-31, so neither tool has its own idea of “now”.

Each question is a pair of files you can download and run: q1-hba1c.sql and q1-hba1c.jq, q2-ed.sql and q2-ed.jq, q3-bp.sql and q3-bp.jq, q4-metformin.sql and q4-metformin.jq, q5-glucose.sql and q5-glucose.jq. The rest of the page uses messy.sql, count.sql, count-obs.jq and to-tx.jq.

Q1: HbA1c above 9% in the last year

HbA1c reflects average blood glucose over the previous few months, and a high value is the classic sign of poorly controlled diabetes. The question names a code (LOINC 4548-4), a threshold, a unit (%) and a window, and asks for patients:

$ docker exec -i pg psql -U postgres -a < q1-hba1c.sql
-- Q1: HbA1c (LOINC 4548-4) above 9% in the last year
SELECT count(*) AS results, count(DISTINCT patient) AS patients
  FROM observations
 WHERE code = '4548-4' AND num > 9 AND date >= '2025-10-31';
 results | patients 
---------+----------
       0 |        0
(1 row)

-- The same question with no time window
SELECT date::date, left(patient::text, 8) AS patient, value
  FROM observations
 WHERE code = '4548-4' AND num > 9;
    date    | patient  | value 
------------+----------+-------
 2018-08-11 | 86755eb9 | 9.7
(1 row)

-- Every type 2 diabetic (SNOMED CT 44054006): latest HbA1c
WITH dm AS (
  SELECT DISTINCT patient FROM conditions
   WHERE code = '44054006'),
ranked AS (
  SELECT patient, date, value, row_number() OVER (
           PARTITION BY patient ORDER BY date DESC) AS n
    FROM observations WHERE code = '4548-4')
SELECT left(dm.patient::text, 8) AS patient,
       r.date::date AS latest, r.value
  FROM dm LEFT JOIN ranked r
    ON r.patient = dm.patient AND r.n = 1
 ORDER BY latest;
 patient  |   latest   | value 
----------+------------+-------
 058228a1 | 2025-12-09 | 6.1
 ee37362c | 2025-12-14 | 6.0

$ cat q1-hba1c.jq
# Q1 over the FHIR export: HbA1c above 9%
[inputs | .entry[].resource
 | select(.resourceType == "Observation")
 | select(any(.code.coding[];
     .system == "http://loinc.org" and .code == "4548-4"))
 | select(.valueQuantity.value > 9)]
| {ever: length,
   patients: (map(.subject.reference) | unique | length),
   last_year: (map(select(.effectiveDateTime >= "2025-10-31"))
               | length),
   values: map([.effectiveDateTime, .valueQuantity.value])}
$ jq -n -c -f q1-hba1c.jq output/fhir/*.json
{"ever":1,"patients":1,"last_year":0,"values":[["2018-08-11T01:47:23-04:00",9.71]]}

Both tools say zero in the last year, and one result ever: a 9.7% in August 2018. A zero is the answer that most needs checking, because a typo in the code also returns zero. The second SQL statement drops the window to prove the filter can match at all, and the third turns the question around: start from the people who should have been tested, the five patients with type 2 diabetes, and show each one's latest result. A LEFT JOIN keeps anyone with no HbA1c at all (a care gap); here all five have a result within the last year. row_number() OVER (PARTITION BY patient ORDER BY date DESC) is the standard way to pick the latest row per patient, and you will write it often.

Look again at the jq output: 9.71, where SQL said 9.7. The CSV rounds values to one decimal; FHIR keeps two. At a threshold of 9 it doesn't matter. Move the threshold onto the rounding and it does:

$ docker exec pg psql -U postgres -Atc \
  "SELECT count(*) FROM observations WHERE code = '4548-4' AND num > 8.2"
1
$ jq -c 'select(.code.coding[0].code == "4548-4")' obs.ndjson \
  | jq -s 'map(select(.valueQuantity.value > 8.2)) | length'
13

One result above 8.2 in SQL, thirteen in jq. Twelve results of 8.21 were written to the CSV as 8.2, which is not above 8.2. The FHIR server we load later agrees with jq. Neither tool is wrong; they were given different numbers. When you compare exports, compare at the precision of the coarser one, and say so.

Q2: ED visits per month

An emergency department visit is an encounter, so this question counts visits, not patients; we show both. The opposite mistake, counting encounters when the question asked about patients, is one of the commonest in this work, so put both numbers side by side until you are sure which one was asked for. The CSV calls the encounter class emergency. FHIR uses the HL7 ActCode EMER. Same idea, different code, and a mapping you must get right:

$ docker exec -i pg psql -U postgres -a < q2-ed.sql
-- Q2: ED visits per month since January 2024
SELECT to_char(start, 'YYYY-MM') AS month,
       count(*) AS visits, count(DISTINCT patient) AS patients
  FROM encounters
 WHERE encounterclass = 'emergency' AND start >= '2024-01-01'
 GROUP BY 1 ORDER BY 1;
  month  | visits | patients 
---------+--------+----------
 2024-02 |      1 |        1
 2024-08 |      1 |        1
 2024-10 |      2 |        2
 2024-12 |      2 |        2
 2025-02 |      1 |        1
 2025-08 |      2 |        2
 2026-06 |      1 |        1
 2026-10 |      1 |        1
(8 rows)

-- October 2024 by day: UTC, then Boston time
SELECT start::date AS utc_day,
       (start AT TIME ZONE 'America/New_York')::date AS local_day
  FROM encounters
 WHERE encounterclass = 'emergency'
   AND start BETWEEN '2024-10-01' AND '2024-11-01';
  utc_day   | local_day  
------------+------------
 2024-10-05 | 2024-10-05
 2024-10-05 | 2024-10-04
(2 rows)
$ cat q2-ed.jq
# Q2 over the FHIR export: ED visits per month
[inputs | .entry[].resource
 | select(.resourceType == "Encounter" and .class.code == "EMER")
 | select(.period.start >= "2024-01-01")
 | {month: .period.start[:7], day: .period.start[:10],
    patient: .subject.reference}]
| group_by(.month)[]
| [.[0].month, length, (map(.patient) | unique | length),
   (map(.day) | join(" "))]
| @tsv
$ jq -n -r -f q2-ed.jq output/fhir/*.json
2024-02	1	1	2024-02-09
2024-08	1	1	2024-08-14
2024-10	2	2	2024-10-04 2024-10-05
2024-12	2	2	2024-12-29 2024-12-25
2025-02	1	1	2025-02-11
2025-08	2	2	2025-08-19 2025-08-08
2026-06	1	1	2026-06-12
2026-10	1	1	2026-10-25

The months agree. The days don't. In October 2024 SQL puts both visits on the 5th, and jq puts one on the 4th. The CSV stores UTC; the FHIR export writes Boston time with its offset, and our jq takes the first ten characters of that local string. A visit late in the evening of 4 October in Boston is already 5 October in UTC. The second SQL statement converts to America/New_York and gets jq's answer. Hospitals report by local day, so local time is usually right for a census; whichever you choose, choose it on purpose. A monthly report can show the same problem when a visit falls near midnight at the end of a month.

Tested: in this Synthea build, the CSV timestamps we looked at end in Z (UTC), and the FHIR export writes the same moments with a -04:00 or -05:00 offset, depending on daylight saving time. Comparing those strings compares local dates, not instants.

Q3: systolic blood pressure of 140 or more

Systolic pressure has its own LOINC code, 8480-6. SQL finds it at once. The obvious jq query finds nothing:

$ docker exec -i pg psql -U postgres -a < q3-bp.sql
-- Q3: systolic BP (LOINC 8480-6) of 140 mm[Hg] or more
SELECT date::date, left(patient::text, 8) AS patient,
       num, units
  FROM observations
 WHERE code = '8480-6' AND num >= 140 AND date >= '2025-10-31'
 ORDER BY 1;
    date    | patient  |  num  | units  
------------+----------+-------+--------
 2025-12-14 | ee37362c | 142.0 | mm[Hg]
 2026-08-16 | c4f2f15f | 145.0 | mm[Hg]
(2 rows)
$ jq -c 'select(.code.coding[0].code == "8480-6")' obs.ndjson | wc -l
0
$ cat q3-bp.jq
# Q3 over the FHIR export. Systolic BP usually lives inside a
# blood pressure panel (LOINC 85354-9) as a component.
inputs | .entry[].resource
| select(.resourceType == "Observation"
         and .effectiveDateTime >= "2025-10-31") as $obs
| (.component // [.])[]
| select(any(.code.coding[];
    .system == "http://loinc.org" and .code == "8480-6"))
| select(.valueQuantity.value >= 140)
| [$obs.effectiveDateTime[:10], $obs.subject.reference[9:17],
   $obs.code.coding[0].code, .valueQuantity.value,
   .valueQuantity.unit]
| @tsv
$ jq -n -r -f q3-bp.jq output/fhir/*.json
2025-12-14	ee37362c	85354-9	142	mm[Hg]
2026-08-15	c4f2f15f	85354-9	145	mm[Hg]

Zero isn't a data problem; it's a modelling difference. In FHIR, a blood pressure is one Observation coded as a panel (85354-9) with the systolic and diastolic values as components, as the Observation page describes. The CSV flattens each component into its own row. The fixed jq looks inside components (and falls back to the resource itself when there are none), and finds the same two readings. Note the second date once more: 2026-08-16 in SQL, 2026-08-15 in jq. Same reading, same time-zone story as Q2.

$ cat q4-metformin.jq
# Q4 over the FHIR export
def coded($sys; $code):
  any(.coding[]?; .system == $sys and .code == $code);
[inputs | .entry[].resource] as $all
| ($all | map(select(.resourceType == "Condition"
    and (.code | coded("http://snomed.info/sct"; "44054006"))
    and .clinicalStatus.coding[0].code == "active")
    | .subject.reference) | unique) as $dm
| ($all | map(select(.resourceType == "MedicationRequest"
    and (.medicationCodeableConcept | coded(
      "http://www.nlm.nih.gov/research/umls/rxnorm"; "860975"))
    and .status == "active")
    | .subject.reference) | unique) as $met
| {diabetics: ($dm | length),
   on_metformin: ($met | map(select(IN($dm[]))) | length)}
$ jq -n -c -f q4-metformin.jq output/fhir/*.json
{"diabetics":5,"on_metformin":5}

Searching display text for “diabetes” finds 17 patients, because 15 patients have prediabetes, and complications like diabetic kidney disease are separate codes. Matching SNOMED CT 44054006 finds 5. If you do want “any diabetes”, build the list of codes on purpose (a value set), don't let a substring build it for you. The join then needs both a code and a state: RxNorm 860975 (24-hour metformin 500 mg) with no stop date. The last statement is the classic trap: 54 metformin rows but only 5 patients, because each refill is a new prescription row. Count DISTINCT patient when the question is about people.

In jq, “today” has to come from different fields: a Condition's clinicalStatus and a MedicationRequest's status. coded is a small helper that matches system + code on any coding, and IN intersects the two patient lists. Both tools say 5 and 5. They agree here because Synthea derives the CSV stop date and the FHIR status from the same event. In a real EHR the two are separate fields with separate errors, and an active order for a patient who died is a common finding.

Q5: glucose and units

The watch-out from the summary: comparing values without converting units. Canadian labs report glucose in mmol/L; Synthea's US-style data is in mg/dL. Suppose a Canadian colleague asks for glucose results of 7.0 mmol/L or more in the last year. Glucose also has two common LOINC codes, for whole blood and for serum or plasma, so we ask for both:

$ docker exec -i pg psql -U postgres -a < q5-glucose.sql
-- Q5: glucose of 7.0 mmol/L or more in the last year.
-- Two LOINC codes; values are mg/dL; 1 mmol/L = 18.016 mg/dL
SELECT code, units, count(*) AS results,
       count(*) FILTER (WHERE num >= 7.0) AS unconverted,
       count(*) FILTER (WHERE num / 18.016 >= 7.0) AS converted
  FROM observations
 WHERE code IN ('2339-0', '2345-7') AND date >= '2025-10-31'
 GROUP BY 1, 2;
  code  | units | results | unconverted | converted 
--------+-------+---------+-------------+-----------
 2339-0 | mg/dL |      20 |          20 |         1
 2345-7 | mg/dL |       1 |           1 |         0
(2 rows)

SELECT date::date, left(patient::text, 8) AS patient, num,
       round(num / 18.016, 1) AS mmol_l
  FROM observations
 WHERE code IN ('2339-0', '2345-7') AND date >= '2025-10-31'
   AND num / 18.016 >= 7.0;
    date    | patient  |  num  | mmol_l 
------------+----------+-------+--------
 2026-09-26 | 86755eb9 | 140.2 |    7.8
(1 row)
$ cat q5-glucose.jq
# Q5 over the FHIR export: convert to mmol/L before comparing
inputs | .entry[].resource
| select(.resourceType == "Observation"
         and .effectiveDateTime >= "2025-10-31")
| select(any(.code.coding[]; .system == "http://loinc.org"
    and (.code == "2339-0" or .code == "2345-7")))
| .valueQuantity as $q
| (if $q.code == "mg/dL" then $q.value / 18.016
   elif $q.code == "mmol/L" then $q.value
   else error("unexpected unit \($q.code)") end) as $mmol
| select($mmol >= 7.0)
| [.effectiveDateTime[:10], .subject.reference[9:17],
   $q.value, ($mmol * 10 | round / 10)]
| @tsv
$ jq -n -r -f q5-glucose.jq output/fhir/*.json
2026-09-26	86755eb9	140.2	7.8

Applied straight to mg/dL values, the 7.0 threshold flags all 21 results. Converted (one mmol/L of glucose is 18.016 mg/dL, from its molar mass of 180.16 g/mol), it flags one. The jq version checks the UCUM unit code on every value and stops with an error on a unit it doesn't know, rather than guessing. That is the behaviour you want: in real feeds, one lab's mmol/L and another's mg/dL arrive under the same LOINC code.

Canada: SI units are the norm in Canadian lab reports, so mmol/L for glucose. If you build a report from US data or from a US vendor's defaults, convert first and print the unit next to every number. Your unit tests should include a value in each unit.

SQL Server and reporting databases

You will rarely query an EHR's live database. Vendors copy it nightly into a reporting database, and that is where analysts work. Epic's Clarity is the best-known example, and it is queried in SQL. Many of these run on Microsoft SQL Server, so if you target Microsoft shops, load the same CSVs into SQL Server and port the five questions to T-SQL. The ideas carry over unchanged: joins, row_number() OVER (…), distinct counts, explicit time zones. The syntax differs in places, for example TOP instead of LIMIT, DATEADD for date arithmetic, and TRY_CAST to turn a non-numeric value into NULL instead of an error; the T-SQL reference has the details. We didn't run SQL Server for this page, so nothing here was tested against it.

Exercises

  1. Why match codes on system + code instead of display text? Use the Q4 output to give two concrete ways display text fails.
  2. Name two honest reasons SQL and jq counts can differ. For each, write the one-line fix that makes them agree, and say which answer you would report.
  3. Which code system holds a lab test? A diagnosis? A drug? A vaccine? A unit? Find one example of each in a Synthea FHIR bundle with jq.
  4. Rewrite Q2 in SQL so both months and days are Boston-local, and show that it now agrees with jq day by day since 2024.
  5. Care gaps: list the patients with type 2 diabetes whose latest HbA1c is more than six months old, or who have none. Do it in SQL with a LEFT JOIN and in jq. Then delete one patient's HbA1c rows and check that both queries still report that patient.
  6. Write a jq program that produces exactly the observation rows the CSV holds for one patient (flatten the components). Which rows can't you produce, and why?
